01 · Search for Agents：让代理从站点自己的域名检索原文

事件简介：Cloudflare 推出 Search for Agents，让站长通过控制台开关建立 AI Search 实例，自动抓取并索引站点内容，再从自有域名提供搜索入口。此前站长需要自行建实例、配置接口，并告诉代理到哪里查询。

技术机制：网络层在 HTML 元数据或 Markdown 页首的 YAML 中公布接口位置与用法。代理可向 /.well-known/search 发 GET，或用 QUERY 方法把查询放进请求正文；结果是带相关度的 Markdown 原文片段，答案由调用方模型组织。

实际影响：编辑判断：维护大型产品文档时，站长可减少另建检索网关和发现协议的接线工作；代理先定位相关段落，再读必要页面，减少逐页遍历。相关度分数仍需结合内容核查。

限制与来源：免费方案也有额度，导入、索引存储与查询沿用 AI Search 计费及限制；可访问性仍受站点机器人管理和网页防火墙配置影响。官方演示不证明所有代理都会识别元数据，也不保证检索完整性。

02 · Omni 接入 PagerDuty：同一告警持续更新一个值班事件

事件简介：Amazon CloudWatch Omni 新增 PagerDuty 集成，把监控告警接入团队现有排班与升级策略。通知带严重程度、受影响服务和返回监控数据的链接；本次改变的是告警处置链路，区别于此前 Azure 遥测导入。

技术机制：接入后还须选择可通知的 PagerDuty 服务，并给告警访问配置授予调用权限。每次投递都会重查权限；默认以告警 ARN 这个资源标识去重，Critical、Warning 等状态触发事件，OK 状态发出恢复通知。

实际影响：编辑判断：同一支付服务反复越过阈值时，可让后续状态更新同一事件，值班者从链接回到原始数据，减少人工转发告警和重新拼接上下文。要自动关闭事件，规则必须包含 OK 状态。

限制与来源：连接账号不会自动加入所有服务；每个 AWS 账户在一个区域只能有一个 PagerDuty 连接。撤销权限会停止已有通知，断开集成也不会停止告警计算。缩短处理时间是厂商预期，公告未给独立对照数据。

06 · pw-loudness-eq：先按应用平衡音量，再在设备输出端防止削波

简介：xoxorwr/pw-loudness-eq 将 Windows 响度均衡处理移植到 Linux 的 PipeWire 音频系统，帮助用户缩小应用内安静与响亮片段的音量差。它提供音频模块和可选 GTK3 控制窗口，可全局或按应用开关。

技术特点：插件在每个播放流混音前运行，把频谱功率汇成二十五个频带来估算响度，再调节整体增益，并非逐频段改变音色的均衡器。设备端另有向前预读的限幅器，在放大后的峰值到来前降低增益，防止输出削波失真。

适用场景与价值：编辑判断：看对白很轻、音效很响的视频时，可减少反复手调音量；语音通话等应用可加入排除名单。设置保存在 PipeWire 元数据对象中，可用命令脚本修改并在重启后保留。

限制与来源：要求 PipeWire 1.4 以上；JACK 客户端、超过八声道的流及直接使用 PipeWire 的 Flatpak 应用不处理。设备限幅器独立常开并增加预读延迟。逆向移植与算法描述来自作者，本期未做听感或数值一致性复测。

技术特点：程序嵌入 postgres:18-alpine 镜像，通过 h9 的 Linux 兼容层运行原有二进制，由 Plan 9 内核回应系统调用。目录锁保证只有一个服务进程；minipg run 将连接地址写入 DATABASE_URL 后运行应用，后续命令复用服务。
