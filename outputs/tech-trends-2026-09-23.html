RapidOCR：把 PaddleOCR 模型带到多种离线运行环境

简介：RapidAI/RapidOCR 是面向应用开发者的开源 OCR 工具，可在 Windows、Linux 与 macOS 上离线识别图片文字，默认覆盖中英文，并提供其他语言模型。当前仓库承载 Python 组件；需要 C++、Java 或 C# 的团队可使用项目拆分出的对应实现。

技术特点：项目将 PaddleOCR 模型转换为兼容性较广的 ONNX 格式，并允许通过 ONNX Runtime、OpenVINO、MNN、Paddle、TensorRT 或 PyTorch 执行检测与识别。调用方以图片路径或数据创建 RapidOCR 推理，得到文字框、内容和置信度；需要专用领域时，可先在 PaddleOCR 微调，再把模型接回部署链。

适用场景与价值：例如文档归档程序可在内网机器上批量提取扫描件文字，不必把文件上传到外部 OCR 服务；多种推理后端让团队按 CPU、GPU 和终端条件选择部署方式，减少为不同环境重写前后处理的工作。

限制与来源：默认语言、识别效果与资源占用取决于所选模型和后端，README 没有提供覆盖所有语言与设备的统一精度承诺；模型权重源自 PaddleOCR，许可与哈希需逐项核对。来源：README：Introduction、Usage、Docker 与 Models

窗口内官方发布 · HTTP 缓存

Cloudflare 为 Cache Rules 加入可配置的 Vary 支持

事件简介：Cloudflare 宣布所有套餐的 Cache Rules 支持 HTTP Vary。同一 URL 可能按 Accept、语言或压缩能力返回不同内容；若缓存只看 URL，会把错误版本发给客户端，而机械地按原始请求头拆分又会产生大量难复用的缓存对象。

技术机制：源站仍用响应头声明哪些请求字段可能改变表示，站点管理员则在规则中决定每个字段如何进入缓存键：对已知协商头做归一化、保留精确值，或在变化不可控时绕过缓存。这样把“源站声明可能变化”与“边缘实际区分哪些变化”拆开，避免将任意请求头直接放大成缓存碎片。

实际影响：同时提供 HTML/JSON、WebP/AVIF 或多语言页面的团队，可以在一个 URL 下保持正确内容协商，并控制命中率与缓存规模；上线前应以真实请求验证归一化规则，防止合并了本应隔离的响应。

限制与来源：这不是自动推断业务语义，规则错误仍会造成错配；Vary: * 等不可预测情形应绕过缓存。来源：Cloudflare 官方技术说明（2026-09-22）

窗口内官方发布 · 模型 API 成本与延迟

OpenAI 为 GPT-6 提示缓存增加断点、诊断与预热

事件简介：OpenAI 发布 GPT-6 提示缓存的新控制与观测能力：开发者可显式选择可复用的提示前缀，在仪表盘查看命中率，并用诊断工具把一次未命中与近期响应比较，定位模型、工具、设置或输入中的变化以及受影响 token 数。

技术机制：长 Agent 会话可把稳定的系统指令、工具定义和参考资料放在缓存断点之前，把易变内容追加在后；工具集合变化时，可保持定义、schema 与顺序稳定，再用 allowed_tools 控制本轮可调用项。GPT-6 还允许通过追加 configuration_update 调整后续推理强度，而不破坏已有缓存，并可在首个用户请求前预热已知上下文。

实际影响：拥有长工具清单或共享知识库的 Agent 服务，可以把缓存未命中从模糊的成本波动变成可定位事件，再针对断点布局和请求构造做优化，降低重复处理前缀带来的首 token 等待与输入费用。

限制与来源：文中的成本和命中率改善来自少数合作方案例，不能直接外推；缓存资格、保留时间和计费仍应以 API 指南与自身负载测量为准。来源：OpenAI 官方公告与 Prompt Caching 指南

Google CC：让家庭成员选择性共享信息给同一个 Agent

事件简介：Google Labs 将实验性 Agent CC 扩展到家庭和同住群体，最多六名成员可共同管理。每个人选择把学校、活动、旅行等邮件、文件、聊天或日历内容交给 CC，它再生成共享的每日简报、更新 Calendar 与 Tasks，并在获得许可后预填报名 PDF 等事务；原公告发布于 9 月 17 日，本期因当前讨论热度作为窗口外补充。

技术机制：每个 CC 拥有独立且已验证的 Google 账号，只响应组内成员；成员可按发件人持续共享，也可逐条转发，群组记忆与个人偏好分开保存。后台为每个 CC 分配由 Antigravity 驱动的隔离云计算机，并连接 Gmail、Chat、Drive、Docs、Calendar 与 Maps API，让自然语言计划能够落实为表单、日历项和文档。

实际影响：家庭不必把所有信息集中到一个人的邮箱，再手工转录到共享日历；显式分享和动作确认也比直接授予整个邮箱访问权更容易说明权限边界。

限制与来源：目前仅面向美国、18 岁以上个人 Google 账号并采用候补机制，仍属 Labs 早期实验；隐私边界与长期准确性只有厂商描述，需持续观察。来源：Google Labs 官方说明（2026-09-17）

AX：用声明式对象约束集群中的 Agent 任务

简介：google/ax 是面向平台工程团队的 Agent 编排控制面，目标是在 Kubernetes 集群中运行大量有状态、会调用模型和工具的自主任务。用户以 YAML 描述 Task、Workspace、Gateway 与 Model，再用类似 kubectl 的 CLI 创建、观察、进入、暂停或恢复任务；它不是构建 Agent 推理逻辑的 SDK。

技术特点：Task 给不受信代码设置 CPU/内存隔离，Workspace 预装 Git 仓库、MCP 服务和技能，Gateway 用主机白名单限制出站网络，Model 从 Kubernetes Secret 读取模型凭据。控制面运行在 Kubernetes 上，并依赖 Agent Substrate 执行沙箱及保存暂停前的状态。

适用场景与价值：内部编码 Agent 平台可把仓库、网络出口和模型权限写进可审查清单，再批量启动任务；空闲任务暂停后保留工作区，避免每次重新准备环境。

限制与后续证据：README 明确警告核心概念、协议和规范仍会发生破坏性变化，部署还要求 Kubernetes、Redis、镜像仓库及可达的 Substrate API。后续应看稳定版 API、升级路径、故障恢复与独立规模基准。来源：README：Why、Quick start 与架构文档

当前 GitHub Trending（全语言榜）· 早期沙箱运行时

Agent Substrate：用少量工作进程复用大量休眠 Actor

简介：agent-substrate/substrate 是在 Kubernetes 上运行有状态 Agent 或其他间歇性应用的执行运行时，不负责定义 Agent 行为。它把逻辑应用称为 Actor，把实际承载进程称为 Worker，并试图利用 Agent 大部分时间等待模型、工具或用户的特点，让数量更多的 Actor 复用较小的 Worker 池。

技术特点：控制面实时把 Actor 分配到 Worker，路由入站请求，并管理创建、销毁、挂起和恢复；快照同时保存内存与文件系统状态，使 Actor 能在另一 Worker 恢复。底层支持 gVisor 与 microVM 等沙箱，Kubernetes 管理 Pod 和伸缩，Substrate 补充 Actor 调度、请求暂存与网络路由。仓库演示在 8 个物理 Pod 上复用约 250 个有状态 Actor，但这是作者示例。

适用场景与价值：大量编码会话或沙箱 MCP 服务可在无请求时释放 Worker 容量，有流量再恢复，降低为每个长寿命会话常驻一只 Pod 的资源浪费。

限制与后续证据：项目明确处于早期开发、不可用于生产且 API 几乎必然变化，仅瞄准最新及前一版 Kubernetes；后续应关注第三方密度测试、快照安全、跨版本恢复和多租户故障隔离。来源：README：架构、状态、Quickstart 与 Benchmarking

当前 GitHub Trending（全语言榜）· 早期视频工具

video-use：让编码 Agent 用转写稿而不是逐帧读取视频

简介：browser-use/video-use 是安装给 Claude Code、Codex 等可执行 shell 的 Agent 技能，面向需要把访谈、教程或口播原片剪成成片的创作者。用户把素材放入目录、确认剪辑策略后，工具输出 edit/final.mp4，可处理赘词、停顿、字幕、调色和动画叠加。

技术特点：它不把全部视频帧送给模型：先调用 ElevenLabs Scribe 为每个素材生成逐词时间戳、说话人和声音事件，再压缩成约 12KB 的 takes_packed.md；遇到含糊停顿或切点时，才生成带胶片帧、波形和词标注的时间轴 PNG。模型产出 EDL（剪辑决定列表）后由 FFmpeg 渲染，并在每个切点检查画面跳变、爆音和字幕遮挡，最多修复重渲染三次。

适用场景与价值：长口播可先按文本定位重录和静音区，再只对候选切点看图，减少逐帧视觉 token 与人工粗剪时间，同时把决策保留为可复查的 EDL。

限制与后续证据：转写依赖 ElevenLabs API 与密钥，渲染依赖 FFmpeg；“自检通过”不等于叙事、事实或审美正确。后续应看不同语言转写误差、长片成本、切点独立评测和真实编辑返工率。来源：README：How it works、Pipeline 与 Design principles
